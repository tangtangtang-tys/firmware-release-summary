01 / 产品概览

为什么建设：从信息分散到可核对闭环

平台把各部门原本分散在版本、审批、说明、设备验证和问题处理中的信息，组织成一套统一决策依据。

建设前：信息分散
当前版本不易判断版本确认依赖多人沟通，难以快速判断当前生效版本。
审批依据容易漂移审批内容与执行内容缺少统一记录，变更后容易产生口径差异。
问题版本难串联历史记录、影响范围和操作依据不容易还原到一次业务事件。
→
建设目标：统一闭环
当前生效版本唯一以系统记录的当前生效版本为准，不以版本号大小推断。
审批内容锁定提交审批后锁定版本和影响范围，执行前再次核对状态。
状态分别确认审批通过、平台生效、设备升级结果分别判断。
全链路留痕审批记录、发布记录和操作日志可以关联追溯。
01 / 产品概览

四个系统，各自承担一段责任

把“平台完成了什么”和“设备侧发生了什么”分开，才能避免跨部门协作时的口径误判。

固件发布平台

版本与审批管理

管理版本、功能项、APP 更新说明、发布 / 回滚 / 下架审批、当前版本和操作记录。

OTA（设备升级系统）

设备侧执行

负责指定设备验证、测试升级、灰度放量、设备升级执行和结果反馈。

APP（用户端）

用户侧触达

展示更新说明，按平台返回的提醒策略触达用户，提供用户侧升级入口。

钉钉

通知与跳转

发送待办、催办和审批结果通知；审批记录以平台审批中心为准。

三条协作边界

平台审批通过
不代表所有设备已升级

平台版本生效
不代表设备执行成功

钉钉通知
不替代平台审批记录

01 / 产品概览

平台位于物联网升级链路的中枢

平台连接研发、测试、产品线、审批人员与设备侧系统，把一次版本发布从“准备”推进到“可追溯的执行结果”。

输入与决策

研发 / 测试提供固件包、版本说明，完成设备验证
产品线 / 审批人员确认范围、风险和上线窗口
固件发布平台版本信息 · 发布治理 · 全链路记录
版本与固件包固件标识、版本、适用机型、校验信息
功能项与 APP 说明功能配置、多语言文案、提醒方式
审批中心发布、回滚、下架审批和审批记录
发布与日志版本生效、操作日志、发布记录和审计

执行与反馈

OTA（设备升级系统）测试、升级执行、灰度放量和设备结果
设备接收升级任务并返回执行结果
APP / 钉钉用户说明、提醒通知和审批跳转
关键边界：平台版本生效代表平台侧切换完成；设备是否升级成功，要以 OTA 执行结果确认。钉钉只负责通知与跳转，审批记录保存在平台审批中心。

03 / 业务流程

先验证，再审批，最后生效

每次发布操作都要完成版本校验、测试验证、审批确认和执行前复核。

正常发布

确认版本与影响范围，完成测试和审批，复核通过后正式生效。

准备版本制品与配置
→
OTA 验证指定设备测试
→
平台审批多级节点
→
执行复核状态与范围
→
版本生效生成发布记录

问题回滚

发现问题后核对版本与影响范围，完成回滚审批，复核后恢复上一发布版本。

识别异常查看版本与日志
→
对比差异版本与配置
→
回滚审批原因与范围
→
复核执行恢复上一版本

版本下架

下架当前生效版本，保留固件包和历史记录；已创建的升级任务需另行核对。

确认原因选择原因类型
→
下架审批确认影响范围
→
执行复核确认当前版本
→
完成下架等待重新发布
统一原则：有审批、有复核、有记录；平台状态与设备升级结果分别确认。
